# PR 문구 — AIP-3022

## Title

```
feat: CR 소유 워크로드에 toleration/affinity 주입 (AIP-3022)
```

## Body

## 개요

워크로드가 아닌 임의 CR 이 소유한 워크로드에 project-managed toleration/affinity 가 주입되지 않는
문제를 고친다. 조사·설계(AIP-3022)와 구현(AIP-3097 · AIP-3098 · AIP-3099)을 한 PR 에 담았다.

`WorkloadControllerReconciler` 가 owner 의 **kind 를 보지 않고** controller ownerReference 존재만으로
조기 반환한다. Deployment→ReplicaSet 중복 처리 방지가 의도였지만, owner 가 임의 CR 이면 그 CR 을
리컨실하는 컨트롤러가 없어 **아무도 toleration 을 주입하지 않는다.** 같은 가정이
`RootWorkloadControllerResolver` 의 미지원 kind 예외로 이어져 `PodReconciler`(파드 삭제)와
`PodReviewHandler`(`_getNodes()` 폴백)까지 번졌다.

설계 문서: `docs/aip-3022-cr-owned-daemonset/01-design.md` (결정 7개 · 근거 · 검증 계획).

## 왜 지금 고치는가 — 파드 레벨에서 이미 손상이 관측된다

cluster12 실측(2026-09-07, 조회 전용). 파드 `trident-node-linux-ck9td`(2026-08-19 생성,
project-managed 노드 `vnode1.pnode7`):

```
{effect: NoExecute,  operator: Exists}                                    ← 유지
{effect: NoSchedule, key: node-role.kubernetes.io/control-plane, Exists}  ← 치환됨
project-managed toleration: 0개
```

웹훅이 폴백 경로로 이 파드를 처리하면서 벤더의 catch-all `NoSchedule` 을 치환하고 **대체 toleration 을
아무것도 주입하지 않았다.** 지금 Running 인 것은 `NoSchedule` 이 바인딩된 파드를 축출하지 않고, 파드
생성이 노드 taint 부착 전이라 스케줄도 통과했기 때문이다. **재생성되는 순간(노드 재부팅 · DaemonSet
업데이트 · drain) Pending 이 된다** — `isolation-mode=strict` 가 아닌 현재의 `lenient` 노드에서 그렇다.

전수 조사: DaemonSet 18개 중 15개는 pm-toleration 6개를 정상으로 받고, cilium 2개는 제외 라벨로
의도된 제외이며, **결함 대상은 `trident/trident-node-linux` 1건**이다. `aipub-node-group` 이
`policy.daemonSet.allowAllDaemonSets: true` 라 정책 선언과 실제가 어긋난 상태였다.

## 변경

### AIP-3097 — 리컨실러 owner kind 대조

- `WorkloadControllerReconciler`: 조기 반환을 `isOwnedBySupportedControllerType()` 으로 축소.
  controller ownerReference 의 `(apiVersion, kind)` 가 supportedTypes 에 있고 그 타입의 informer 가
  등록돼 있을 때만 스킵한다. 대조 키는 `K8sObjectTypeKey` — kind 단독 비교가 아니다.
- `WorkloadControllerFactory`: `createController(List<? extends K8sObjectType<?>>)` 오버로드 추가.
  `ControllerFactory` 인터페이스와 다른 20여 개 팩토리는 무변경(무인자 `createController()` 는
  `UnsupportedOperationException`, 호출 지점 20곳 전수 확인 결과 도달 불가).
- `ControllerConfiguration`: `resolveSupportedWorkloadTypes()` 단일 수집 지점을 만들어
  `controllerManager` 빈과 `rootControllerResolver` 빈이 **같은 값**을 쓰게 했다. 두 곳이 갈라지면
  리컨실러와 root resolver 의 root 정의가 달라진다.

### AIP-3098 — root 해석 재귀 중단 + 파드 삭제 분기 제거

- `RootWorkloadControllerResolver`: `getObject` → `findObject`(`Optional`). 미지원 kind ·
  informer 미등록 · **캐시에 부모 없음** 세 경우를 모두 "여기서 root 해석을 멈춘다" 로 동일하게
  취급한다. `Objects.requireNonNull` 제거.
  - 세 번째가 설계에 없던 추가 결정이다. NPE 는 `UnsupportedControllerException` 이 아니라서 웹훅
    catch 를 통과했고, pods 웹훅은 `failurePolicy: Ignore` 라 **toleration 0개로 조용히 통과**였다.
  - 파드 레벨은 부모 미해석 시 파드 자신이 아니라 `Optional.empty()` 를 반환한다. 파드를 root 로
    주면 `CompositeWorkloadControllerNodesResolver` 에 `V1Pod` resolver 가 없어 다시 예외가 된다.
    `empty` 는 네임스페이스 Project 폴백으로 흘러 **제거된 `_getNodes()` 와 동일한 결과**다.
- `PodReconciler`: `catch (UnsupportedControllerException) → deletePod` 분기만 제거.
  **`allowedProjectNodes` 밖 파드 삭제와 strict 조기 반환은 그대로 유지** — "모르면 지운다" 만
  폐기하고 격리 강도는 유지한다.

### AIP-3099 — 웹훅 폴백 제거

- `PodReviewHandler`: try/catch 제거, `podNodesResolver.getNodes(pod)` 직접 호출.
- `PodNodesResolver`: `_getNodes()` 와 `//todo` 제거(`getNodes()` 의 root-없음 분기는 유지 — 제거
  대상은 그 복사본이었다).

### 변경하지 않은 것

- `ReconciliationService` — 0 라인. `project == null` 경로가 기존 nodeAffinity term 을 보존하는 동작에
  운영 DaemonSet 15개가 의존한다.
- `UnsupportedControllerException` 클래스와 `CompositeWorkloadControllerNodesResolver` 의 방어 —
  계약 명시용으로 남겼다(도달 불가).
- Deployment/StatefulSet 이 `DefaultWorkloadControllerNodesResolver` 를 쓰는 비대칭 — 의도로 확정.
  `daemonSetPolicy` 를 non-DaemonSet 으로 확장하면 프로젝트 미바인딩 네임스페이스의 임의 워크로드가
  project-managed 노드에 올 수 있어 격리 모델이 깨진다(설계 결정 5).
- CRD · RBAC · `application.yaml` — 변경 없음.
